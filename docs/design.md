# ソフトウェアファクトリー 設計たたき台

Nov 22, 2026 · @tatsuya

## 全体像

常駐プログラム(以下「事務局」)が時間と記録を管理し、判断はすべてClaudeに委ねます。Claudeは常駐させず、事務局がイベントのたびに起動します。

| 役割 | 実体 | 起動のきっかけ | 担当 | 触れてよいもの |
| --- | --- | --- | --- | --- |
| 事務局 | Nodeの常駐プロセス | 常時稼働 | 時計、永続化、キュー、再試行、プロセスの起動と監視、GitHub同期、指示の検査 | SQLite、GitHub API、ワーカーの起動 |
| 司令塔 | Claude(1回ごとの呼び出し) | イベントと定時 | 優先順位、着手の可否、人間に聞くかの判断、報告の要約 | 読み取りのみ。指示をJSONで返す |
| ワーカー | Claude Code(ヘッドレス) | 司令塔の指示 | 計画、実装、レビュー | 自分の作業場所の中のファイルとコミット |
| 対話エージェント | Claude Code(対話型、superpowers有効) | 人間が開く | 起票、質問と回答の取り次ぎ、報告 | イシューの作成とコメント |

設計の原則は3つです。

- 事務局は判断しない。司令塔は実行しない。
- 人間に見える状態はGitHubに、実行の内部情報はSQLiteに置く。
- mainへのマージは人間だけが行う。

## イシューの状態と遷移

イシューの状態は `state:` で始まるラベル1つで表し、人間の対応が必要なのは `needs-info`、`in-review`、`failed` の3つだけです。

&#91;embedded content: イシューの状態遷移 · 8状態\]

色の付いた3つが人間の対応待ちです。`failed` からは、人間が方針をコメントすると `triage` に戻ります(図では省略)。

| ラベル | 意味 | 次に動くのは |
| --- | --- | --- |
| `state:triage` | 新規、または再判定待ち | 司令塔 |
| `state:needs-info` | 情報不足。質問コメントつき | 人間 |
| `state:blocked` | 依存先のイシューが未完了 | 事務局(依存先のクローズを監視) |
| `state:ready` | 着手可能 | 司令塔(着手を指示) |
| `state:in-progress` | ワーカーが作業中 | ワーカー |
| `state:in-review` | PR作成済み | 人間(マージまたは修正依頼) |
| `state:failed` | 試行上限に達した | 人間(方針をコメント) |

完了はラベルではなく、イシューのクローズで表します。補助ラベルは `priority:p0`〜`p3`、`size:s`/`m`/`l`、`agent:skip`(エージェントは触らない)です。

### 遷移表

| 遷移元 | 遷移先 | 条件 | 実行者 |
| --- | --- | --- | --- |
| (新規) | triage | イシューが作成された | 事務局 |
| triage | ready | 受け入れ条件が明確で、依存がない | 司令塔 |
| triage | needs-info | 不明点がある | 司令塔(質問をコメント) |
| triage | blocked | 依存先が未完了 | 司令塔 |
| needs-info | triage | 人間がコメントで回答した | 事務局 |
| blocked | triage | 依存先がクローズされた | 事務局 |
| ready | in-progress | 司令塔が着手を指示し、同時実行の枠がある | 事務局 |
| in-progress | in-review | PRが作成され、テストとレビューを通過した | 事務局 |
| in-progress | needs-info | ワーカーが質問を返して終了した | 事務局 |
| in-progress | ready | 失敗したが試行回数に余裕がある(待機後に再試行) | 事務局 |
| in-progress | failed | 試行上限に達した | 事務局 |
| in-review | in-progress | 人間がPRに修正を依頼した | 事務局 |
| in-review | (クローズ) | 人間がマージした | GitHub |
| failed | triage | 人間が方針をコメントした | 事務局 |

事務局は、この表にない遷移を司令塔が指示しても実行しません。

### 段階1での着手

段階1には司令塔がいないので、`ready` から `in-progress` への遷移の条件のうち「司令塔が着手を指示し」を、次の決まった規則で代えます。遷移そのものは表のとおりで、実行者も事務局のままです。

- **順序:** `priority:` の高い順(`p0` が最初、ラベルなしは最後)に拾い、同じならイシュー番号の若い順にします。
- **拾わないもの:** 起票者が `issues.allowed_authors` にいないイシュー、`agent:skip` の付いたイシュー、待機時間が過ぎていないイシューは拾いません。
- **枠:** `limits.max_parallel` と、1日の実行数の上限(「ワーカーの封じ込め」の「Claudeの認証と利用量の上限」)を超えるときは拾いません。イシューは `ready` のまま残ります。

順序を固定の規則にするのは、事務局が判断を持たないためです。優先度は人間がラベルで決め、事務局は並べるだけにします。段階2で、この規則は司令塔の `start` に置き換えます。

- **リポジトリをまたぐ順:** 優先度が同じなら、ファクトリー側の設定に書いた順で先のリポジトリを先にします。1日の上限が全体の合計なので、どれを先に数えるかを決めておくためです。
- **着手の条件に使う内容:** 起票者、本文、`agent:skip` の有無は、同期のときに `issues` に保存します(`author`、`body`、`agent_skip`)。起票者が分からない行には着手しません。起票者のログイン名は、大文字と小文字を区別せずに照らします。
- **`dry_run` の間:** 着手も、途中の実行を進めることも、状態の変更もしません。ラベルを書けないと、GitHubから見えないところで作業が進み、「人間に見える状態はGitHubに置く」に反するからです。人間が状態を変えた実行の取り消しと、試行回数のリセットは、DBだけの操作なので行います。

### 実行の管理と、状態の進め方

メインループは、ポーリングのたびに、同期の後で次を行います(`src/office/supervisor.ts`)。実行そのもの(ステップ)は、ループの外で進めます。ステップは数時間かかりうるので、待っている間も、同期と、人間による変更への追従を続けるためです。

イシューの状態は、ステップの実行の中では変えません。毎回、DBにあるイシューの状態(GitHubの写し)と実行の記録を見て、行うことを純粋関数(`src/office/settle.ts`)で決めます。入力が記録だけなので、「ステップは終わったが、ラベルを変える前に落ちた」場合も、起動し直せば同じ答えが出て、続きから進みます。

| イシューの状態 | 実行の記録 | 行うこと |
| --- | --- | --- |
| `ready` | 実行中で、まだ何も始めていない | `in-progress` に進めて、実行を進める(着手の続き) |
| `in-progress` | 実行中で、誰も進めていない | 続きを進める(起動時の再開) |
| `in-progress` | 実行中で、publish まで終わっている | `in-review` に進める |
| `in-review` | 実行中で、残りは cleanup だけ | クローズを待つ |
| クローズ済み | 実行中で、残りは cleanup だけ | cleanup を行い、実行を終える |
| 上のどれでもない | 実行中 | 実行を取り消す(人間が状態を変えた) |
| `in-progress` | 最新の実行が `question` | 質問をコメントして、`needs-info` に進める |
| `in-progress` | 最新の実行が `failed`、試行に余裕がある | `ready` に戻す |
| `in-progress` | 最新の実行が `failed`、試行の上限に達した | `failed` に進める |

- **状態の変更:** 事務局が状態を変えるときは、必ず `src/office/transition-apply.ts` を通します。遷移元はDBから読み、遷移表にある変更だけを、ラベルの付け替え(`github.ts` の `setStateLabel`)として実行します。表にない変更は、実行せずに、イベント(`issue.transition_rejected`)とログ(`transition.rejected`)に残します。`decisions` は司令塔の判断の記録なので、ここには使いません。
- **事務局の変更と人間の変更の見分け方:** 事務局は、ラベルを書いた直後に、DBの状態も同じ値にします。そのため、同期が見つける食い違いは、人間の変更だけになります。同期が取得した内容を取り込む途中で事務局がラベルを変えると、古い内容を人間の変更と見誤るので、同期と状態の変更は、リポジトリごとに1つずつ順に行います(`src/office/locks.ts`)。また、GitHubの一覧は、ラベルを変えた直後に変更前の内容を返すことがあります。同期は、更新時刻(`github_updated_at`)が進んでいない内容からは、状態を読みません。事務局の変更も人間の変更も更新時刻を進めるので、進んだ内容が届いたときに読めば足ります。
- **取り消し:** 事務局が進めている間のイシューの状態は `in-progress` だけです(publish の後は `in-review` かクローズ)。それ以外になっていたら、人間が変えたものとして、実行を取り消し、実行中のステップを止めます。取り消しの後は、GitHubの状態に従うだけで、事務局からは書き込みません。作業場所は消しません。
- **cleanup:** PRを作った後、実行は cleanup を残したまま、イシューのクローズを待ちます。待っている実行は、`limits.max_parallel` に数えません。
- **質問のコメント:** コメントには、実行ごとの目印(`<!-- factory:question run=<番号> -->`)を付けます。書く前に、そのイシューのコメントを読み、同じ目印があれば書きません。コメントの後、ラベルを変える前に落ちても、同じ質問が重なりません。
- **試行回数のリセット:** イシューが `failed` を離れたら、それまでの失敗を試行に数えなくします。人間がラベルを手で変えた場合は、同期が記録した「`failed` からの変更」のイベントを見て、その時刻までに終わった失敗をリセットします。イベントは消費せず、時刻で区切るので、何度同期しても結果は変わらず、戻した後の失敗を巻き込みません。事務局が `failed` から `triage` に戻す場合(人間が方針をコメントしたとき。この処理は、まだありません)は、`transition-apply.ts` がリセットします。
- **失敗の隔離:** 1つの実行、1つのイシューの後処理、1つのリポジトリで起きた失敗は、ログに出して、ほかの処理を続けます。記録は残るので、次のポーリングでやり直します。実行を扱うのは、そのポーリングで同期に成功したリポジトリだけです。
- **ステップの中の例外:** そのステップの失敗(`failed`)として記録します。実行は失敗で終わり、待機後に再試行されます。
- **ステップの上限:** plan と review は30分・50ターン、implement は2時間・200ターン、verify はコマンド1つごとに30分です。いまは `src/office/runner.ts` の定数で、設定には出していません。

### 終了のときの動き

SIGTERMとSIGINTを受けたら、実行中のポーリングを終え、進めている実行を止めてから終了します。

- **実行中のステップは待ちません。** ステップは数時間かかることがあり、コンテナの停止の猶予には収まらないからです。起動係への依頼を中断すると、起動係がワーカーのコンテナを止めます(「隔離と起動」の「後始末」)。
- **記録は、実行中のまま残します。** 止めた後に返ってきた結果は、中断によるものかもしれないので、記録しません。次の起動で、そのステップからやり直します。どのステップもやり直して安全なので、PRやコメントは重複しません。
- **中断したワーカーの呼び出しは、ログの場所だけを残します。** 中断した呼び出しのログは、起動の失敗とは区別して、`status` を `interrupted` として書きます。コンテナを止めるので、終了コード、セッション、費用、標準出力は残りません。ログの場所は、実行中のままのステップの `steps.interrupted_log_paths` に足します。ステップの状態と結果は書きません。再開は同じ行を使うので、再開したステップから、中断した呼び出しのログを辿れます。
- **作業場所は片付けません。** 止めたワーカーが残した途中の状態は、次の起動でやり直すワーカーに、そのまま渡ります(「ワーカーの実行手順」の「再開のときの作業場所」)。コミットしていない変更と追跡していないファイルを消してからやり直す案は、次の理由で採りませんでした。
  - 消すには、事務局が作業場所で、内容を書き換えるgit(`git reset`、`git clean`)を実行することになります。作業場所のgit設定はワーカーが書き換えられ、取り出しのときに動くフィルターなどを通して、事務局の権限でコマンドを起動できます。すでにある作業場所で事務局が実行するgitは、ブランチの有無を読むものだけ、という前提(「作業場所」の「すでにある作業場所」)を崩します。
  - 消しても、壊れた依存は直りません。依存の置き場所は、ふつうgitの無視対象で、追跡していないファイルを消す操作の対象になりません。どちらの案でも、ワーカーに入れ直させる必要があります。
  - 途中の状態は、中断のほかに、失敗した実行の次の試行でも残ります(同じ作業場所を使うためです)。指示書で伝えておけば、どちらにも効きます。
  - implement は長くかかることがあり、消すと、そこまでの作業を失います。
- **残したものが、そのままPRに入ることはありません。** PRに入るのは、コミットされた内容だけです。review の差分も publish も、作業場所ではなく、ミラーに取り込んだコミットを見ます。verify は作業場所でコマンドを実行するので、コミットしていない変更が残っていると、その影響を受けます。そのため verify は、コマンドの前に、コミットされていない内容が残っていないことを確かめ、残っていれば差し戻します(「verify の動き」の「コミットされていない内容」)。implement の指示書も、終了するときにコミットしていない変更を残さないことを求めています。
- **試行には数えません。** 同じ実行の再開として扱います。
- **猶予:** 止まるのを8秒まで待ちます(Dockerの停止の猶予の既定は10秒)。過ぎたら、待たずに終了します。

## 司令塔の入出力

司令塔は状態の要約をJSONで受け取り、決まった種類の指示をJSONで返すだけの関数として扱います。

### 呼ばれるタイミング

- イシューの作成、または人間によるコメントや編集
- ワーカーの完了、質問、失敗
- 定時の見直し(例: 毎朝と、1時間ごと)
- 対話エージェント経由の割り込み(「これを最優先で」など)

短時間に続いたイベントは、30秒ほど待ってまとめて1回で渡します。

### 渡すもの

- きっかけとなったイベント
- 未クローズのイシュー一覧(番号、タイトル、状態、優先度、規模、依存、最終更新)
- きっかけのイシューの本文と直近のコメント
- 進行中の実行(イシュー、現在のステップ、経過時間、試行回数)
- 直近の失敗と、前回却下された指示
- 枠(同時実行の空き、当日の残り予算)

### 返せる指示

| 指示 | 引数 | 事務局の検査 |
| --- | --- | --- |
| `triage` | issue、state(ready / needs-info / blocked)、priority、size、depends\_on | 対象が triage である |
| `ask_human` | issue、question | 質問文が空でない |
| `start` | issue | ready である。枠と予算がある。依存がすべてクローズ済み |
| `reprioritize` | issue、priority | 対象が未クローズである |
| `cancel` | run | 実行中である |
| `report` | kind、body | なし(報告のキューに入る) |
| `noop` | なし | なし |

すべての指示に `reason` を必須とし、判断の記録に残します。検査に落ちた指示は実行せずに却下として記録し、次回の入力に含めます。

```json
{
  "commands": [
    { "type": "triage", "issue": 12, "state": "ready", "priority": "p1", "size": "s", "depends_on": [], "reason": "受け入れ条件が3点とも検証可能" },
    { "type": "ask_human", "issue": 8, "question": "CSVの文字コードはUTF-8でよいですか", "reason": "出力仕様が未指定" },
    { "type": "start", "issue": 12, "reason": "p1で依存なし、枠が1つ空いている" }
  ]
}
```

## ワーカーの実行手順

1回の実行は7つのステップを順に進み、ステップが終わるたびにチェックポイントを保存します。Claudeが担当するのは計画、実装、レビューの3つで、残りは事務局がコードで行います。

| ステップ | 実行者 | 内容 | チェックポイントに残すもの |
| --- | --- | --- | --- |
| 1. prepare | 事務局 | 作業場所(イシューごとのclone)とブランチ `agent/issue-<番号>` を作る | 作業場所のパス |
| 2. plan | Claude | イシューを読んで計画を書く。不明点があれば質問を返して終了する | 計画の本文 |
| 3. implement | Claude | 実装し、テストを書き、コミットする | コミットのハッシュ |
| 4. verify | 事務局 | テストとlintをコマンドで実行する | 終了コードとログ |
| 5. review | Claude(新しい文脈) | イシュー、差分、テスト結果だけを見て判定する | 判定と指摘 |
| 6. publish | 事務局 | pushしてPRを作り、`in-review` に進める | PR番号 |
| 7. cleanup | 事務局 | マージまたはクローズの後に作業場所を消す | なし |

- **差し戻し:** verify の失敗と review の修正要求は implement に戻します。1回の実行の中で2回までです。
- **ステップの結果:** 終わったステップは、`done`(次へ進む)、`rework`(差し戻し)、`question`(質問を返して終了)、`failed`(失敗して終了)のいずれかを `steps.status` に残します。次に行うことは、この記録だけから決まります。
- **再開:** 事務局が落ちたら、最後のチェックポイントの次のステップからやり直します。どのステップも、やり直して安全な作りにします(ブランチがあれば使う、PRがあれば更新する)。
- **再開のときの作業場所:** 消さずに、そのまま残します。止めたワーカーが残したもの(積んだコミット、コミットしていない変更、追跡していないファイル、入れかけで壊れた依存)は、やり直すワーカーがそのまま受け取ります。事務局は、再開であることをワーカーに伝えず、渡す入力も変えません。代わりに、implement と review の指示書に、途中の状態が残りうることと、そのときの進め方を常に書いておきます。implement は、`git status` と `git log` で確かめ、残っていたものを確かめてから使うか捨て、依存が壊れていれば `setup` をやり直します。review は、残っているものを判定の根拠にせず、手も付けません。理由は「終了のときの動き」にあります。
- **上限:** Claudeの各ステップにターン数の上限とタイムアウトを設けます。どちらに達した場合も、そのステップは `failed` になります。
- **試行の上限:** 1つのイシューに対する実行は、製品の `factory.yml` の `limits.max_attempts` 回までです(既定は3回)。上限に達したら `failed` にします。上限を製品側に置くのは、どこまで自動で粘るかが製品ごとに違うからです。
- **待機時間:** 失敗して `ready` に戻したイシューは、1回目の失敗の後は5分、2回目の後は30分、3回目以降は2時間待ってから再試行します。値はファクトリー側の設定(`retry_wait_minutes`)に置きます。上限が3回なら、使うのは5分と30分の2つです。間隔を伸ばすのは、一時的な障害(レート制限、通信の失敗)は短い待機で直り、直らない失敗を短い間隔で繰り返しても利用枠を使うだけだからです。
- **試行に数えるもの:** 実行が `failed` で終わった場合だけを数えます。質問を返して終了した場合、人間のラベル変更で取り消された場合、事務局の再起動で同じ実行を再開した場合は数えません。どれもワーカーの失敗ではないからです。
- **試行回数のリセット:** 人間が `failed` のイシューを戻したら、それまでの失敗は数えません。次の実行は1回目になり、待機時間も最初の値に戻ります。人間が方針を示した後は、別の取り組みとして扱うからです。実行の記録は消さず、リセットした時刻(`runs.attempt_reset_at`)を残します。
- **結果の形式:** Claudeのステップは `done` / `question` / `failed` のいずれかと要約をJSONで返します。review だけは、修正要求として `rework` も返せます。plan と implement が `rework` を返した場合は、`failed` として扱います。事務局は、申告ではなくコミットやPRの実在を確かめてから状態を進めます。形式に合わない出力(JSONでない、必須項目がない、未知の状態)は、理由を要約に入れて `failed` として扱います。
- **ログ:** Claudeの呼び出しごとに、実行したコマンド、終了コード、標準出力、標準エラーを1つのファイルに残し、場所を `steps.log_path` に記録します。置き場所は `<logs_dir>/<owner>/<name>/issue-<番号>/<開始時刻>-<ステップ>.log` です。ワーカーが書き換えられないように、作業場所の外(事務局のデータの置き場所)に置きます。指示書と入力は写さず、大きさだけを残します。事務局の停止で中断した呼び出しのログは、`steps.log_path` ではなく `steps.interrupted_log_paths`(パスのJSON配列)に残します(「事務局の停止」の「終了のときの動き」)。
- **定期タスク:** スケジュールがイシューを起票し、以降は通常のイシューと同じ経路を通ります。

### verify の動き

verify は、ワーカーの申告に頼らず、製品の `factory.yml` にあるコマンドを実行して合否を決めます。

- **コマンドの読み元:** 作業場所のファイルではなく、事務局が同期して保存した `factory.yml`(既定ブランチのもの)から読みます。作業場所のファイルはワーカーが書き換えられ、検査そのものを差し替えられるからです。`factory.yml` が未取得または不正な場合と、作業場所のcloneがない場合は、状態の確認もコマンドも実行せずに失敗させます。
- **実行の場所:** コマンドごとに、起動係を通して、ワーカーと同じ種類の使い捨てのコンテナで `sh -c <コマンド>` を実行します。作業ディレクトリは製品のcloneです。コンテナに渡る環境変数は起動係が決める一覧だけで、事務局の環境変数は引き継ぎません。Claudeのトークンは求めません。
- **コミットされていない内容:** コマンドが検査するのは作業場所のファイルで、PRに入るのはコミットされた内容です。食い違ったまま合格にしないように、コマンドの前に、作業場所にコミットしていない変更(ステージしただけのものを含みます)と、追跡していないファイルがないことを確かめます。あれば、コマンドを1つも実行せずに不合格(`rework`)にし、残っているパスを指摘として implement に渡します。片付けるのは implement で、事務局は作業場所を書き換えません(「終了のときの動き」)。
  - **無視対象:** gitの無視対象(依存の置き場所など)は、残っていても止めません。`setup` が作るものだからです。
  - **確かめ方:** `git status` を、事務局の中ではなく、検査コマンドと同じく起動係を通したコンテナの中で実行します。作業場所のgit設定はワーカーが書き換えられ、事務局の権限でコマンドを起動できるからです。時間の上限は5分です(コマンドの上限のほうが短ければ、そちら)。
  - **確かめられなかった場合:** `git status` が0以外で終わった、時間切れになった、起動係に届かない、のどれも、差し戻しではなく `failed` にします。コマンドは実行しません。
  - **指摘に載せるパス:** 先頭の50件までで、残りは件数だけを残します。改名は、消したパスと足したパスの両方を挙げます。
  - **別の場所で検査する案:** コミットされた内容だけを取り出した場所でコマンドを実行する案は、採りませんでした。作業ディレクトリを変えるために起動係の依頼の形を変える必要があり、依存を毎回入れ直すことにもなるからです。
  - **防げないもの:** 防ぐのは、コミットし忘れと、途中の状態の残りです。ワーカーは、作業場所のgit設定や `.git/info/exclude` で、ファイルを無視対象に見せられます。無視対象の中身(依存)を書き換えて検査を通すこともできます。わざと行うすり抜けは、ここでは防げません。また、作業用のブランチ以外が取り出されている場合と、verify の後に積まれたコミットは、確かめていません。
- **順序:** `setup`、`test`、`lint` の順に実行します。`setup` が通らなければ、残りは実行しません。`test` が通らなくても `lint` は実行します。差し戻しは2回までなので、1回の差し戻しで両方の指摘を渡すためです。
- **合否:** すべてのコマンドが終了コード0なら合格(`done`)、1つでも0以外なら不合格(`rework`)です。判定に使うのは終了コードだけです。
- **時間の上限:** コマンド1つごとに設けます。過ぎたら、起動係がコンテナごと止めるので、子プロセスも残りません。時間切れは不合格(`rework`)として扱います。
- **実行できなかった場合:** 起動係に届かない、依頼を拒否されたなど、コマンドを実行できなかった場合は、差し戻しではなく `failed` にします。製品の側の失敗ではないからです。
- **チェックポイント:** コマンドごとの状態、終了コード、所要時間と、合格しなかったコマンドの出力の末尾、残っていたコミットされていないパスを残します。出力の末尾は、差し戻しのときに implement へ渡せます(ログは作業場所の外にあり、ワーカーからは読めないためです)。
- **ログ:** verify 1回につき1つのファイルに、状態の確認と、コマンドごとの標準出力と標準エラーを残します。置き場所は、Claudeの呼び出しのログと同じ規則(`<開始時刻>-verify.log`)です。製品のテストはワーカーが書いた内容を出力できるので、トークンに見える文字列(`sk-ant-` で始まる)は、ログと結果に残す前に伏せます。

### publish の動き

publish は、ワーカーの申告に頼らず、コミットの実在、作者、差分を事務局が自分で確かめてから、push してPRにします。保護対象のパスに触れた変更は、最後の網としてここで止めます。

- **取り込み:** 作業場所のcloneから、作業用のブランチ(`agent/issue-<番号>`)を事務局専用のミラーに取り込みます。ミラーの側で `git fetch` を実行するので、作業場所の側のフックは動かず、作業場所のgit設定にある、コマンドを起動する項目も効きません。`repo` や `.git` がリンクなどに差し替えられている場合は、たどらずに失敗させます。
- **作者:** 既定ブランチになく、作業用のブランチにあるすべてのコミットについて、作者(author)とコミッター(committer)の名前とメールアドレスが、ファクトリー側の設定(`commit_author`)と完全に一致することを確かめます。1つでも一致しなければ、push せずに `author_mismatch` として返します。結果とログ(`publish.stopped`)には、一致しなかったコミットのハッシュと、そこに書かれていた作者とコミッターを残します。作業場所のgit設定ではなく、ミラーに取り込んだコミットそのものを読むので、ワーカーが設定や環境変数を変えても、結果は変わりません。取得元にもとからあるコミットは検査しません。照合は純粋関数(`src/office/authors.ts`)です。コミットは書き換えず、署名と、コミットメッセージの中の記述(`Co-Authored-By` など)は見ません。
- **差分:** 作業場所ではなく、ミラーで調べます。基準は、既定ブランチと分かれた位置で、PRに現れる差分と同じです。改名は1つにまとめず、消したパスと足したパスの両方を検査します。
- **規則の読み元:** `paths.forbidden` と `paths.protected` は、verify と同じく、事務局が同期して保存した `factory.yml` から読みます。作業場所のファイルはワーカーが書き換えられるからです。
- **パターンの書き方:** `*`(区切りをまたがない)、`?`、`**`(0個以上のディレクトリ)、末尾の `/`(`dir/**` と同じ)に対応します。リポジトリの直下からの一致で見るので、`CLAUDE.md` は直下のものだけに当たり、どの階層でも当てたいときは `**/CLAUDE.md` と書きます。大文字と小文字は区別します。対応していない書き方(`[`、`{`、否定の `!` など)があるときは、当たらないものとして通さずに、publish を失敗させます。照合は純粋関数(`src/office/paths.ts`)で、依存は足していません。読めないパターンは、同期の時点の検証でも同じ関数で見つけて、`factory.yml` を不正として扱います(「製品側の契約」)。そのため、publish のこの検査に当たるのは、検証をすり抜けた内容が保存されていた場合だけで、最後の網として残しています。
- **結果:** 次の表のとおりです。検査で止まった場合は、push もPRの作成もしません。

| 結果 | 場合 | ステップの結果 |
| --- | --- | --- |
| `published` | push して、PRを作った(または更新した) | `done` |
| `dry_run` | 検査は通ったが、`dry_run` なので書き込んでいない | `done` |
| `no_commits` | 既定ブランチにないコミットがない(ブランチがない場合を含む) | `failed` |
| `author_mismatch` | 作者かコミッターが `commit_author` と一致しないコミットがある | `failed` |
| `empty_diff` | コミットはあるが、差分が空 | `failed` |
| `forbidden` | `paths.forbidden` に当たる変更がある | `failed` |
| `needs_approval` | `paths.protected` に当たる変更がある。人間の承認待ち | `failed` |

- **検査の順:** コミットの有無、作者、差分が空か、`paths.forbidden`、`paths.protected` の順に見て、最初に当たったものを結果にします。
- **承認待ち:** `needs_approval` は、結果の種類と `awaitingApproval` で、ほかの失敗と見分けられます。人間が承認して進める仕組みは、まだありません。両方に当たるパスは `forbidden` として扱います。
- **push:** ミラーから、作業用のブランチだけを同じ名前で push します。それ以外のブランチ名は、push の関数が断ります。作業用のブランチはファクトリーだけが使うので、差し戻しで履歴が変わっていても通るように、上書きで push します。フックは動かしません。トークンは実行時の環境変数だけで渡し、gitの設定、URL、引数、ログ、DBに残しません。
- **PR:** 同じブランチのオープンなPRがあれば、作らずにタイトルと本文を更新します。タイトルはイシューのタイトルです。取り込み先は既定ブランチです。
- **PRの本文:** 前半に事務局が確かめたこと、後半にワーカーの申告を書き、末尾に目印(`<!-- factory -->`)を付けます。組み立ては純粋関数(`buildPrBody`)で、同じ入力からは同じ本文になります。
  - **前半(事務局が確かめたこと):** 対応イシュー(`Closes #<番号>`)、「検証結果」(検査コマンドごとの結果の表。出力は載せません)、「未検証の範囲」(`verify.unverified` に当たる範囲)です。
  - **後半(ワーカーの申告):** 区切りの線と、「ここから下は、ワーカー(Claude)の申告です。事務局は、中身を確かめていません。」という断り書きの後ろに、「実装の要約(ワーカーの申告)」と「レビューの結果(ワーカーの申告)」の節を置きます。中身は、`done` で終わった最後の `implement` と `review` の要約(`steps` の `output`)です。差し戻しがあった実行では、最後のやり直しのものになり、差し戻しのときの指摘は載りません。`plan` の要約は載せません。
  - **順の理由:** 要約はワーカーの出力で、製品のイシューやリポジトリの文章の影響を受けます。事務局が確かめた検査結果とは信頼の度合いが違うので、見出しと断り書きで分けます。要約の中身が本文を崩しても前半に及ばないように、後ろに置きます。断り書きから本文の末尾までが、ワーカーの申告です。要約の中に、前半と同じ名前の見出しが書かれていても、事務局が書いたものではありません。
  - **要約がない場合:** 節は残し、「要約の記録がありません。」と書きます。
  - **長すぎる場合:** 要約1つにつき20,000文字を上限にします。越えた分は、行の区切りで切り、「(長いので、ここから先を省略しました。全文は事務局の記録にあります)」と書きます。2つとも上限いっぱいでも、GitHubの本文の上限(65,536文字)に収まります。
  - **要約の無害化:** 事務局は、要約の中身を解釈しません。見出しの有無も検査しません。本文のほかの部分やGitHubの動きに作用する書き方だけを、次のように機械的に崩します(`sanitizeSummary`)。コードの中かどうかは見分けません。見分けを誤ると、すり抜けになるためです。そのため、コードの中の記号も置き換わります。

    | 対象 | 扱い | 防ぐもの |
    | --- | --- | --- |
    | トークンに見える文字列(`sk-ant-` で始まる) | ログと同じ伏せ方で伏せる | トークンの掲載 |
    | HTMLコメントの始まり(`<!--`) | `<` を全角(`＜`)に変える | 要約の中の目印と、後ろを隠す閉じないコメント |
    | イシューを閉じる書き方(`Closes #1`、`fixes owner/name#2` など) | `#` を全角(`＃`)に変える。URLで書いたものは `:` を全角(`：`)に変える | マージで、対応イシューのほかのイシューが閉じること |
    | メンション(`@name`) | `@` を全角(`＠`)に変える | PRの本文から、人やチームに通知が飛ぶこと |
    | 閉じていないコードブロック(切り詰めた場合を含む) | 閉じる | 後ろの節と目印が、コードブロックに巻き込まれること |

  - **防がないもの:** 要約の節の中の見た目の崩れ(閉じない `<details>` など)は、防ぎません。影響は、ワーカーの申告の中にとどまります。
- **やり直し:** 何度行っても、ブランチは同じ内容になり、PRは1つのままです。push の後、PRを作る前に止まった場合は、次の呼び出しがPRを作ります。
- **書き込みの場所:** push、PRの作成と更新、イシューへのコメントは、`src/office/github.ts` の書き込み関数だけが行い、どれも `dry_run` を確認します。マージを行う口は作りません。publish は、DBには書かず、結果を返すだけです。記録と `in-review` への遷移は、ステップを実行する側が行います。
- **コメント:** publish は、イシューにコメントしません。やり直しのたびに同じコメントが重なるのを避けるためです。コメントの書き込み関数は、目印を付けて書きます。

## SQLiteスキーマ

テーブルは8つで、`issues` だけがGitHubの写し、残りは事務局だけが持つ実行の記録です。

```sql
CREATE TABLE schema_version (version INTEGER NOT NULL);

-- repo は owner/name 形式。複数リポジトリを扱うため、1製品目から持たせる

-- GitHubイシューの写し(正はGitHub)
CREATE TABLE issues (
  repo              TEXT NOT NULL,
  number            INTEGER NOT NULL,
  title             TEXT NOT NULL,
  state             TEXT NOT NULL,   -- triage / needs-info / ... / closed
  priority          TEXT,
  size              TEXT,
  depends_on        TEXT,            -- JSON配列
  author            TEXT,            -- 起票者のログイン名
  body              TEXT,            -- 本文
  agent_skip        INTEGER NOT NULL DEFAULT 0,  -- agent:skip が付いていれば 1
  github_updated_at TEXT NOT NULL,
  synced_at         TEXT NOT NULL,
  PRIMARY KEY (repo, number)
);

-- 事務局が受け取ったイベントのキュー
CREATE TABLE events (
  id           INTEGER PRIMARY KEY,
  type         TEXT NOT NULL,
  repo         TEXT,
  issue_number INTEGER,
  payload      TEXT NOT NULL,        -- JSON
  created_at   TEXT NOT NULL,
  handled_at   TEXT
);

-- 司令塔の判断の記録
CREATE TABLE decisions (
  id            INTEGER PRIMARY KEY,
  event_id      INTEGER REFERENCES events(id),
  repo          TEXT NOT NULL,
  command       TEXT NOT NULL,       -- JSON
  reason        TEXT NOT NULL,
  result        TEXT NOT NULL,       -- applied / rejected
  reject_reason TEXT,
  created_at    TEXT NOT NULL
);

-- イシュー1件に対する1回の実行
CREATE TABLE runs (
  id            INTEGER PRIMARY KEY,
  repo          TEXT NOT NULL,
  issue_number  INTEGER NOT NULL,
  attempt       INTEGER NOT NULL,
  status        TEXT NOT NULL,       -- running / done / question / failed / cancelled
  current_step  TEXT,
  worktree_path TEXT,
  branch        TEXT,
  pr_number     INTEGER,
  started_at    TEXT NOT NULL,
  finished_at   TEXT,
  next_retry_at TEXT,
  attempt_reset_at TEXT             -- 値のある失敗は、試行に数えない
);

-- ステップごとのチェックポイント
CREATE TABLE steps (
  id          INTEGER PRIMARY KEY,
  run_id      INTEGER NOT NULL REFERENCES runs(id),
  name        TEXT NOT NULL,         -- prepare / plan / implement / ...
  status      TEXT NOT NULL,         -- running / done / rework / question / failed / cancelled
  output      TEXT,                  -- JSON
  session_id  TEXT,
  cost_usd    REAL,
  log_path    TEXT,                  -- 最後まで終わった呼び出しのログ
  interrupted_log_paths TEXT,        -- 中断した呼び出しのログ(パスのJSON配列)
  started_at  TEXT NOT NULL,
  finished_at TEXT
);

-- 実行中の実行はイシューごとに1つ、実行中のステップは実行ごとに1つ
CREATE UNIQUE INDEX runs_one_running_per_issue
  ON runs (repo, issue_number) WHERE status = 'running';
CREATE UNIQUE INDEX steps_one_running_per_run
  ON steps (run_id) WHERE status = 'running';

-- 定期タスク
CREATE TABLE schedules (
  id             INTEGER PRIMARY KEY,
  repo           TEXT NOT NULL,
  name           TEXT NOT NULL,
  cron           TEXT NOT NULL,
  issue_template TEXT NOT NULL,      -- JSON
  enabled        INTEGER NOT NULL DEFAULT 1,
  last_fired_at  TEXT,
  UNIQUE (repo, name)
);

-- 人間に伝える報告(repo が空なら全体の報告)
CREATE TABLE reports (
  id           INTEGER PRIMARY KEY,
  repo         TEXT,
  kind         TEXT NOT NULL,        -- daily / alert
  body         TEXT NOT NULL,
  created_at   TEXT NOT NULL,
  delivered_at TEXT
);
```

段階0の具体化で、リポジトリごとの同期位置を持つテーブルを1つ追加しました。

```sql
-- リポジトリごとの同期状態
CREATE TABLE repos (
  repo                 TEXT PRIMARY KEY,   -- owner/name
  issues_synced_until  TEXT,               -- イシューの取得済み位置
  comments_synced_until TEXT,              -- コメントの取得済み位置
  factory_yml          TEXT,               -- 検証済みの内容(JSON)

```

`runs.worktree_path` には、イシューごとの作業場所のパスを入れます。段階1で作業場所をworktreeから独立したcloneに変えましたが、適用済みのスキーマは書き換えないので、列の名前はそのままにします。

## GitHubとの同期

食い違ったときは常にGitHubを信じ、GitHubへの書き込みは事務局だけが行います。

- **取り込み:** 最初はポーリングで始めます(1分ごとに、更新されたイシューとPRを取得)。Webhookは公開エンドポイントが必要なので後回しにします。
- **書き出し:** ラベルの変更、コメント、push、PR作成はすべて事務局が行います。ワーカーはコミットまでで、GitHubのトークンを持ちません。
- **人間がラベルを手で変えた場合:** 事務局はそれに従います。実行中の作業があれば取り消します。
- **コメントの区別:** エージェントが書いたコメントには目印(`<!-- factory -->`)を付け、人間のコメントと見分けます。
- **認証:** 対象リポジトリだけに限定したトークンを使い、権限はイシュー、PR、コンテンツの読み書きに絞ります。mainはブランチ保護で直接pushを禁止します。

## ワーカーの封じ込め

ワーカーの範囲は「禁止する」のではなく「できない状態にする」ことで守ります。`gh` や `git push` を打てても、認証情報がなければ何も起きません。

| 層 | 内容 | 強さ |
| --- | --- | --- |
| 資格情報を渡さない | ワーカーの環境にGitHubのトークン、`gh` の認証ファイル、gitの資格情報ヘルパー、SSH鍵を置かない。HOMEを事務局と分ける | 主たる防御 |
| ネットワークを絞る | ワーカーを外への経路がないネットワークに置き、出口をプロキシ1つにする。EC2のインスタンスメタデータ、ホスト、ほかのコンテナには届かせない。宛先の許可リストは段階1の後に足す | 強い |
| ツールの許可設定 | `gh`、`git push`、`curl` などを拒否リストに入れる | 補助(シェル経由で回避できる) |
| 事務局による検査 | pushの前に差分を調べ、保護対象のパスに触れていたら人間の承認待ちにする | 最後の網 |

### 隔離と起動

ワーカーは、ステップごとに使い捨てのコンテナで動かします。コンテナを立てるのは事務局ではなく、Dockerソケットを持つ小さな常駐コンテナ(以下「起動係」)で、事務局は起動係に依頼します。

```text
事務局(GitHubのトークンとDBを持つ。Dockerソケットなし)
   │ リポジトリ、イシュー番号、ステップの種類、実行する内容
   ▼
起動係(Dockerソケットを持つ。トークンなし)
   │ 依頼を検査して、コンテナを立てる
   ▼
ワーカーのコンテナ(1ステップごとに使い捨て)
   見えるもの: そのイシューの作業場所と、ワーカー用のHOMEだけ
```

- **起動係が受け付けるのは、決まった形の依頼だけです。** マウントするパスは、リポジトリ名とイシュー番号から起動係が自分で組み立てます。任意のパスのマウント、特権の付与、イメージの指定は、依頼では行えません。イメージはファクトリー側の設定から起動係が読みます。
- **起動係はトークンを持たず、製品のコードもイシューの文章も読みません。** 信頼できない入力に触れないので、ソケットを持たせても攻撃の入口を狭く保てます。
- **事務局と起動係のやりとり** は、両者だけが共有するボリューム上のUnixソケットで行います。ワーカーのコンテナには、このボリュームをマウントしません。
- **ワーカーのコンテナ** は、事務局と同じく権限を落とします(`cap_drop: ALL`、`no-new-privileges`、メモリとプロセス数の上限)。ルートのファイルシステムは読み取り専用で、書けるのは作業場所と `/tmp` だけです。環境変数は、起動係が明示した一覧だけを渡します。
- **起動係のコンテナ** は、ネットワークにつなぎません。持つのは、Dockerソケット、事務局と共有するソケット、設定ファイル(読み取り専用)だけです。
- **後始末:** 時間の上限を過ぎた場合と、依頼した事務局がいなくなった場合は、起動係がコンテナを止めます。起動係が起動するときに、前回残ったワーカーのコンテナを消します。
- **verifyも同じ経路で動かします。** 製品のテストを実行するコンテナには、Claudeのトークンも渡しません。
- **イメージ:** 既定は、このリポジトリで作る基本イメージ(Node、git、Claude Code)です。製品に固有のツールが要る場合は、ファクトリー側の設定でリポジトリごとに別のイメージを指定します。イメージの指定を製品の `factory.yml` に置かないのは、ワーカーの変更で実行環境が差し替わるのを避けるためです。

この形にした理由は次のとおりです。

| 検討した案 | 採らなかった理由 |
| --- | --- |
| 事務局のコンテナの中で、別ユーザーとして動かす | 事務局は `cap_drop: ALL` と `no-new-privileges` で動いており、ユーザーを切り替えられない |
| 事務局をホストで動かし、別ユーザーで起動する | 事務局のコンテナによる保護を捨てることになる。ユーザーの違いだけでは、ネットワークの制限と、イシュー間や製品間の分離ができない |
| 事務局にDockerソケットを渡す | ソケットを持つプロセスはホストのroot相当になる。信頼できない入力を扱い、トークンを持つ事務局が、ホスト全体に届くようになる |
| トークンのないワーカー用コンテナを常駐させる | 1つのコンテナに全部の作業場所が見え、ほかのイシューやほかの製品のコードを読み書きできる |

起動係を挟むと、事務局が乗っ取られた場合に届く範囲は、GitHubのトークンとDBまでにとどまります。

### 外向き通信

段階1では、ワーカーから内部への通信を「できない状態」にし、外部への通信は宛先を絞らずに通します。

- **経路:** ワーカーのコンテナは、Dockerの `internal` 指定で作った、外への経路がないネットワークに置きます。インスタンスメタデータ、ホスト、ほかのコンテナには、経路がないので届きません。
- **出口:** 同じネットワークにプロキシのコンテナを1つ置き、外へ出る通信は環境変数(`HTTPS_PROXY` など)でそこを通します。
- **プロキシの規則:** リンクローカル、プライベート、ホスト宛てを拒否し、それ以外のHTTPSを通します。通すのは443番への `CONNECT` だけで、平文のHTTPは通しません。判定は、名前ではなく、名前を引いた後のIPアドレスで行い、判定したアドレスにそのままつなぎます。内部のアドレスを指す名前を用意されても、通さないためです。
- **プロキシの実体:** このリポジトリのコード(`src/proxy/`)で、Nodeの標準機能だけで作っています。判定を純粋関数にしてテストでき、依存もイメージも増えないからです。
- **段階1の後:** 宛先の許可リスト(ClaudeのAPI、パッケージレジストリ)を、プロキシの設定として足します。

ホストのファイアウォールではなくプロキシにしたのは、ホストの設定を変えずに済み、許可リストを後から同じ場所に足せるからです。許可リストを段階1に入れないのは、必要な宛先が製品ごとに違い、実際の製品で通してからでないと決められないからです。

段階1で残る穴は3つです。

- **外部への持ち出しは防げません。** ワーカーは、製品のコードと自分のClaudeのトークンを、任意の外部サイトに送れます。GitHubのトークンとDBは、そもそも見えないので持ち出せません。
- **プロキシに対応しないツールは通信できません。** 製品のセットアップやテストが独自に通信する場合は、接続エラーとして失敗します。
- **同時に動くワーカー同士は、通信できます。** 同じネットワークにつながるためです。Dockerの設定でコンテナ間の通信を止めると、プロキシにも届かなくなります。段階1は同時実行が1件なので、このままにします。

### 作業場所

worktreeは使わず、イシューごとに独立したcloneを作ります。

| 場所 | 中身 | 見えるのは |
| --- | --- | --- |
| `<repos_dir>/<owner>/<name>.git` | 事務局専用のミラー。GitHubとの取得とpushはここから行う | 事務局だけ |
| `<work_dir>/<owner>/<name>/issue-<番号>/repo` | イシューごとのclone。ミラーから作る | 事務局と、そのイシューのワーカー |
| `<work_dir>/<owner>/<name>/issue-<番号>/home` | ワーカーのHOME。Claude Codeのセッションが残る | 事務局と、そのイシューのワーカー |

- **置き場所:** `repos_dir` と `work_dir` はファクトリー側の設定から読みます。`repos_dir` は事務局のデータ用ボリュームの中に、`work_dir` はそれとは別のボリュームに置きます。ワーカーのコンテナには、`work_dir` のうち、そのイシューのディレクトリだけをマウントします。
- **所有者:** どちらも事務局の実行ユーザーです。ワーカーのコンテナも同じuidで動かします。分離はユーザーの違いではなくマウントで行うので、uidをそろえて、所有者の付け替えを不要にします。
- **置き場所の検査:** `repos_dir` と `work_dir` は絶対パスで書き、一方がもう一方の内側にある設定は通しません。作業場所のパスは、事務局が作るときも起動係がマウントするときも、同じ関数で組み立てます。
- **ミラー:** 取得元のブランチは `refs/remotes/origin/*` に置きます。取得元のURLは取得のたびに引数で渡し、リモートとしては登録しません。
- **作り方:** 作業場所のcloneは `git clone` ではなく、空のリポジトリにミラーから取得して作ります。リモートの設定が残らず、ミラーとオブジェクトのファイルを共有(ハードリンク)することもないからです。既定ブランチは、差分の基準としてローカルブランチに残します。隣の名前(`repo.partial`)で作り、できあがってから `repo` に改名するので、`repo` があれば準備は終わっています。
- **資格情報:** 作業場所のcloneのリモートは空にします。GitHubのURLもトークンもミラーのパスも入れません。事務局がミラーでGitHubと通信するときも、トークンはコマンドの実行時にだけ環境変数で渡し、gitの設定、URL、コマンドの引数に残しません。
- **コミットの作者:** ワーカーのコンテナにはユーザーのgit設定がありません。そのままでは作者が決まらずコミットが失敗するので、prepare が作業場所のcloneを作るときに、cloneのgit設定(`user.name`、`user.email`)に作者を書きます。作者はファクトリー側の設定(`commit_author`)から読み、全製品で同じものを使います。既定値は `factory-worker` と `factory-worker@example.invalid` です。メールアドレスは、実在の宛先に届かない予約済みのドメイン(`.invalid`)にします。名前とメールアドレスには、`<`、`>`、改行を使えません。先頭と末尾には、空白、制御文字、記号(`.`、`,`、`:`、`;`、`"`、`'`、`\`)を使えません。gitがコミットに書くときに落とすので、コミットの作者が設定と一致しなくなり、作者の検査で止まるからです。`.` を落とすかはgitの版で違いますが(ワーカーのイメージの2.39は落とします)、落とすものとして扱います。途中にあるものは使えます。このような値は、設定の読み込みで断ります。自動テストは、テストを実行する環境のgitを使うので、ワーカーのイメージのgitとの食い違いには気づけません。設定の検証を通る値を、ワーカーのイメージのgitがそのままコミットに書くことは、`scripts/check-isolation.sh` が、実際にコンテナでコミットを作って確かめます(Dockerが要ります)。例は、自動テストと同じ一覧(`scripts/commit-author-examples.ts`)から読みます。作者を書くのは作るときだけで、すでにある作業場所には書きません。設定を変えた場合、反映されるのは、その後に作る作業場所からです。
- **作者の検査:** ワーカーは、作業場所のgit設定、環境変数(`GIT_AUTHOR_NAME` など)、`git commit --author` で、作者を変えられます。指示書で禁じるだけでは守れないので、事務局が取り込みのときに確かめます。既定ブランチから作業用のブランチまでのすべてのコミットについて、作者とコミッターが `commit_author` と一致しなければ、push しません(「publish の動き」の「作者」)。すでにある作業場所でコミットを重ねた後に `commit_author` を変えると、前の作者のコミットが一致しなくなり、publish は止まります。
- **すでにある作業場所:** prepare は、作業場所がすでにあれば中身を変えずに使います。そこで事務局が実行するgitは、ブランチの有無を読むものだけです。`repo` がディレクトリでない場合(リンクへの差し替えなど)と、ブランチが消されている場合は、作り直さずに失敗させます。中断したステップの再開と、失敗した実行の次の試行でも、同じ作業場所をそのまま使うので、前回の途中の状態が残っていることがあります(「ワーカーの実行手順」の「再開のときの作業場所」)。
- **取り込み:** 事務局は、作業場所のcloneからミラーにワーカーのコミットを取り込み、コミットの作者と差分を検査してからpushします。事務局がgitを実行するときは、フックを無効にし、作業場所の側のgit設定を信用しません。gitの呼び出しは `src/office/git.ts` に集め、フックの場所、`core.fsmonitor`、資格情報ヘルパーを毎回上書きし、事務局の環境変数を引き継ぎません。

worktreeをやめた理由は2つです。そのイシューの作業場所だけをマウントすると、worktreeは親の `.git` を参照できず動きません。また、worktreeは `.git` を共有するので、ワーカーがほかのブランチの参照、gitの設定、フックを書き換えられます。独立したcloneなら、どちらも起きません。

### Claudeの認証と利用量の上限

- **認証:** Claudeのサブスクリプションを使います。`claude setup-token` で発行した長期トークンを、環境変数 `CLAUDE_CODE_OAUTH_TOKEN` として、plan、implement、reviewのコンテナにだけ渡します。トークンは起動係の環境変数に置き、事務局、DB、ログ、作業場所には書きません。
- **理由:** 従量課金が発生せず、費用の上限をサブスクリプションの枠で抑えられます。
- **1日の上限:** 金額ではなく、着手する実行の数で守ります。UTCの1日に開始した実行(再試行を含む)が `daily_run_limit`(既定20)に達したら、その日は新しく着手しません。数え方が固定なので、事務局の判断にはなりません。上限は全リポジトリの合計です。枠がリポジトリではなくサブスクリプションに付いているからです。
- **1回の上限:** ステップごとのターン数とタイムアウトで守ります。
- **費用の記録:** `claude -p` が返す金額(`total_cost_usd`)を `steps.cost_usd` に残しますが、サブスクリプションでは請求額ではなく参考値です。サブスクリプションのトークンで実際に呼び出して、金額が0ではなく、使ったトークン数を定価で計算した値で返ることを確かめました(小さな呼び出し1回で約0.08ドル)。ターン数の上限に達した場合も返ります。時間切れで止めた場合は、結果を受け取れないので記録できません。
- **注意:** 利用枠は、人間が対話で使うClaude Codeと共有です。ワーカーが使い切ると、人間の作業も止まります。枠に達したときの失敗は、通常の失敗と同じく待機して再試行します。

ファクトリー側の設定に足す項目は、次のとおりです。

```yaml
repos_dir: /data/repos            # 事務局専用のミラーの置き場所
work_dir: /work                   # イシューごとの作業場所の置き場所
logs_dir: /data/logs              # ワーカーの呼び出しのログの置き場所。work_dir と repos_dir の外に置く
retry_wait_minutes: [5, 30, 120]  # 失敗後の待機時間。回数が足りなければ最後の値を使う
daily_run_limit: 20               # UTCの1日に着手する実行の数の上限(全リポジトリの合計)
worker_image: factory-worker      # ワーカーの既定のイメージ
commit_author:                    # 省略可。ワーカーのコミットの作者。先頭と末尾に空白や記号を置かない
  name: factory-worker
  email: factory-worker@example.invalid   # 実在の宛先に届かないものにする
repos:
  - repo: owner/name
    token_env: GITHUB_TOKEN_EXAMPLE
    worker_image: owner-name-worker   # 省略可。製品に固有のツールが要る場合
```

## 対象リポジトリとの関係

対象リポジトリの設定はワーカーの振る舞いを変えるので、何を読み込むかを役割ごとに明示し、リポジトリ側にもファクトリー向けの取り決めを置きます。

### 設定の干渉

| リポジトリ内のもの | 起きうる干渉 | 方針 |
| --- | --- | --- |
| `CLAUDE.md`、`.claude/rules` | 「ユーザーに確認する」など対話前提の指示が、無人実行では推測や停止になる | ワーカーは読み込む。指示書で「確認が要る場面は質問を返して終了」と読み替えを明記する |
| スキル、プラグイン | 承認待ちを挟む手順が起動して止まる | ユーザー設定は読み込まない。プロジェクトのスキルは棚卸しして、無人で使えるものだけ残す |
| フック | 通知やフォーマッタがワーカー内でも走る。フック自体をワーカーが書き換えられる | 無人で害がないか確認する。`.claude/` の変更は保護対象にする |
| `settings.json` の権限 | リポジトリ側の許可がワーカーの権限を広げる | 事務局が渡す拒否設定を優先させる |
| `.mcp.json` | 外部サービスにつながるツールがワーカーに渡る | ワーカーでは無効にする |
| イシュー本文、コメント、リポジトリ内の文章 | 埋め込まれた指示に従ってしまう | データとして扱う。起票者の許可リストを設け、それ以外は自動で着手しない |

読み込む設定の範囲は、省略時の挙動に頼らず役割ごとに必ず明示します。司令塔は何も読み込まず、ワーカーはプロジェクト設定だけ、対話エージェントはユーザー設定も含めて読み込みます。

### リポジトリ側に必要な取り決め

- **ファクトリー向けの設定ファイル:** セットアップ、テスト、lintのコマンドと、変更禁止のパスを書きます(例: `factory.yml`)。どれも非対話で1コマンドで動くことが条件です。
- **検証できない範囲の明示:** DBなど外部サービスに依存するテストがワーカー環境で動かないなら、対象外と書き、PRに「未検証」と記載させます。
- **イシューテンプレート:** 受け入れ条件、範囲外、依存を書く欄を設けます。
- **ブランチとPR:** ブランチ名は `agent/issue-<番号>`。PRテンプレートに対応イシューと検証結果の欄を置きます。
- **ブランチ保護:** mainへの直接pushを禁止し、CIの成功と人間のレビューを必須にします。
- **保護対象のパス:** `.github/`、`.claude/`、`CLAUDE.md`、ファクトリー設定ファイルは、CODEOWNERSで人間のレビューを必須にします。
- **CIのシークレット:** シークレットを使うワークフローは、エージェントのPRでは走らせないか、承認制にします。
- **既存の自動化との重複:** イシューやコメントに反応する別のエージェント用ワークフローがあれば、どちらかに寄せます。

ルールの置き場所は次のように分けます。どのリポジトリにも共通する工程のルールはファクトリーの `prompts/` に、リポジトリ固有の事実(コマンド、禁止パス、規約)はリポジトリ側に置きます。

## 製品とファクトリーの境界

製品固有の知識はすべて製品のリポジトリに置き、ファクトリーのコードには製品名も製品固有のコマンドも書きません。製品の追加は、リポジトリに設定ファイルを置くだけで済むようにします。

| 層 | 製造業でいうと | 中身 | 置き場所 |
| --- | --- | --- | --- |
| 設備 | 汎用機、搬送、工程管理システム | 状態遷移、キュー、再試行、チェックポイント、封じ込め、報告 | ファクトリー |
| 治具と標準書 | 治具、作業標準書、検査基準 | ビルドとテストのコマンド、規約、禁止パス、レビュー基準 | 製品のリポジトリ |
| 個別指示 | 製造指示書 | 受け入れ条件、範囲、依存 | イシュー |

物理のラインと違い、作業者のClaudeは標準書を読めば製品に合わせて動けます。製品ごとの違いは文書で吸収し、設備が製品から受け取るのは、確実性が要る検査(コマンド)と安全(パス)だけにします。

### 製品側の契約

製品のリポジトリ直下に `factory.yml` を置きます。

```yaml
version: 1
level: A                 # 対応水準: A / B / C
commands:                # 非対話で動き、終了コードで合否が分かること
  setup: npm ci
  test: npm test
  lint: npm run lint
verify:
  unverified:            # ワーカー環境では確かめられない範囲
    - DBに接続する結合テスト
paths:
  protected:             # 変更に人間の承認が要る
    - .github/**
    - .claude/**
    - CLAUDE.md
    - factory.yml
  forbidden:             # ワーカーは変更しない
    - migrations/**
limits:
  max_parallel: 1
  max_attempts: 3
issues:
  allowed_authors:       # ここにない起票者のイシューは自動で着手しない
    - your-github-login
```

事務局は、同期のときに `factory.yml` を検証し、通ったものだけを保存します。不正な場合は保存せず、`repo.config_invalid` のイベントとログ(`product.config_invalid`)に、どの項目がなぜ不正かを残します。

`paths.protected` と `paths.forbidden` のパターンは、書き方もこの検証で確かめます。使えるのは `*`、`?`、`**`、末尾の `/` だけです(意味は「publish の動き」の「パターンの書き方」)。それ以外の書き方(`[`、`{`、否定の `!`、先頭の `/` など)が1つでもあれば、`factory.yml` の全体を不正として扱い、何番目のどのパターンがなぜ読めないかを記録します(例: `paths.forbidden.1: パスのパターンを読めません: "secrets/{a,b}.txt"(使えるのは *、?、** だけです)`)。読めるかの判定には、publish の照合と同じ関数を使うので、検証に通ったパターンが publish の時点で読めないことはありません。ワーカーが計画から実装までを終えた後ではなく、着手の前に分かるようにするためです。保存済みの内容も、verify と publish が読むたびに同じ検証をやり直します。

設定ファイルのほかに、製品は次の2点を満たします。

- イシューに受け入れ条件が書かれている。
- 規約が `CLAUDE.md` などに文書化されている。

契約を満たせない製品は、製品側を直すか、対応水準を下げます。ファクトリーを製品に合わせて改造することはしません。

### 対応水準

| 水準 | 製品の状態 | ファクトリーの関与 |
| --- | --- | --- |
| A | 自動テストが揃っている | 起票からPRまで自律で進める |
| B | テストが一部、または外部依存で動かない | PRは作るが「未検証」を明示し、人間の確認を厚くする |
| C | 自動検証の手段がない | 起票、整理、優先順位付け、報告まで。実装は人間 |

### 工程の違い

1製品目は既定の7ステップで固定します。2製品目で実際に食い違った箇所だけを設定に切り出します。切り出すときも、ステップの種類は3つ(Claudeに任せる、コマンドを実行する、人間の承認を待つ)に固定し、製品側が選べるのは並べ方と中身だけにします。

### 境界を守るための確認

- ファクトリーのコードと `prompts/` に、製品名や製品固有のコマンド、パスが出てこない。
- 製品を追加するとき、ファクトリーのコード変更が0行で済む。
- 1製品目から `issues`、`runs`、`schedules` の各テーブルにリポジトリの列を持たせる。
- 失敗は原因で2つに仕分ける。その製品だけで起きるなら製品側の治具や標準書を直し、どの製品でも起きるならファクトリーを直す。

## デプロイの単位

1つのファクトリーが複数のリポジトリを扱える作りにし、デプロイはリポジトリごとではなく信頼境界ごとに分けます。

| 部分 | 方針 | 理由 |
| --- | --- | --- |
| 管理(事務局、司令塔、対話エージェント、ダッシュボード) | リポジトリをまたいで共有する | 人間の注意と、マシンやAPIの枠を全体で配分できる |
| 実行(ワーカーの環境、clone、検査コマンド) | リポジトリごとに分離する | ある製品のワーカーが別の製品のコードに届かないようにする |

別のデプロイに分けるのは、次のいずれかに当てはまる場合です。同じコードを別の設定で立てます。

- 持ち主や契約が違う(仕事用と個人用、別の組織)。トークン、扱ってよいデータ、費用の負担先が異なる。
- ネットワークが違う(特定の環境からしか届かない依存がある)。
- ファクトリーの新版を、重要でない製品で先に試したい。

1製品目から守ることは3つです。

- 状態のテーブルにリポジトリの列を持たせる。
- リポジトリごとの設定(トークン、cloneの場所、上限)を、ファクトリー側の設定ファイルの一覧から読む。
- 司令塔への入力はリポジトリ単位で組み立てる。リポジトリ間の配分(同時実行数、予算、重み)は事務局のコードで行う。

## 技術構成

TypeScriptとNodeで1つのリポジトリにまとめ、EC2上でDocker Composeにより常駐させます。

| 用途 | 候補 |
| --- | --- |
| SQLite | better-sqlite3 |
| GitHub API | Octokit |
| Claudeの呼び出し | `claude -p` をサブプロセスで呼ぶ(下の「Claudeの呼び出し方」) |
| 入出力の検査 | zod |
| スケジュール | cron式を扱える小さなライブラリ |
| APIとダッシュボード | ExpressとReact |
| テスト | Vitest |

```text
factory/
  src/
    office/            事務局
      main.ts          起動とメインループ
      db.ts            SQLiteとマイグレーション
      github.ts        同期と書き出し
      transitions.ts   遷移表と指示の検査
      scheduler.ts     定期タスク
      run-steps.ts     ステップの進み方(純粋関数)
      runs.ts          実行とステップの記録、再開の対象の検索
      runner.ts        ステップの実行
      intake.ts        着手の順と条件(純粋関数)
      settle.ts        記録から、次に行うことを決める(純粋関数)
      transition-apply.ts  遷移表での検査と、状態の変更
      supervisor.ts    着手、再開、取り消し、状態の変更
      locks.ts         リポジトリごとの排他
      verify.ts        検査コマンドの実行と合否(verify)
      publish.ts       取り込み、作者と差分の検査、pushとPRの作成(publish)
      authors.ts       コミットの作者の照合(純粋関数)
      paths.ts         変更されたパスと、禁止や保護対象のパターンの照合(純粋関数)
      step-log.ts      ステップのログの書き出しと、トークンの伏せ字
    agents/
      conductor.ts     司令塔の呼び出し
      worker.ts        plan / implement / review の呼び出し
      prompts.ts       指示書の読み込み
      schemas.ts       入出力の型
    api/               ダッシュボード用の読み取りAPI
    launcher/          起動係(ワーカーのコンテナを立てる)と、事務局から依頼する口
    proxy/             ワーカーの出口になるプロキシ
  prompts/             conductor.md, plan.md, implement.md, review.md
  migrations/          001_init.sql ...
  dashboard/           React
  docker/              ワーカーのイメージ
  scripts/             確認用のスクリプト
  tests/
  docker-compose.yml
```

- **プロセスの配置:** 事務局が1コンテナで、APIとダッシュボードの配信も兼ねます。常駐するコンテナは、ほかに起動係とプロキシの2つです。ワーカーは、事務局の依頼を受けた起動係が、ステップごとに使い捨てのコンテナとして立てます(「ワーカーの封じ込め」の「隔離と起動」)。
- **隔離:** DBファイルとGitHubのトークンは、ワーカーから見えない場所に置きます。事務局はDockerソケットを持ちません。
- **指示書:** プロンプトはコードと分けて `prompts/` に置き、変更履歴を追えるようにします。
- **superpowers:** 司令塔とワーカーでは無効にし、対話エージェントだけで使います。

### Claudeの呼び出し方

ワーカーのステップ(plan、implement、review)は、ワーカーのコンテナの中で `claude -p` を1回実行して行います。

- **理由:** ワーカーは事務局と別のコンテナで動くので、Agent SDKを使うには、コンテナの中で動くNodeのラッパーを別に作ることになります。必要な機能はCLIのフラグで足り、事務局に依存を足さずに済みます。
- **結果の受け取り:** `--output-format json` で、結果、セッションID、金額を受け取ります。結果の形は `--json-schema` で指定し、受け取った側でもzodで検証します。
- **上限:** 時間は、起動係がコンテナごと止めることで守ります。ターン数は `--max-turns` で指定します。固定した版(2.1.330)のヘルプには載っていませんが、実際に呼び出して、上限に達すると `subtype` が `error_max_turns` の結果で終わることを確かめました。ヘルプにないフラグなので、版を上げるときは `scripts/check-worker.sh` で確かめ直します。
- **読み込む設定:** `--setting-sources project` でプロジェクト設定だけを読み、`--strict-mcp-config` でMCPを無効にします(`--mcp-config` を渡さないので、1つも読み込まれません)。
- **権限:** `--permission-mode bypassPermissions` で、確認を挟まずに実行させます。無人の実行には承認に答える人がおらず、できることの範囲はコンテナで守っているからです。事務局が渡す拒否設定(`gh`、`git push`、`curl`、`wget`)は `--disallowedTools` で指定します。
- **指示書と入力:** 引数ではなく、標準入力で渡します。入力(イシューの内容、`factory.yml` の内容など)は、指示書(`prompts/` のファイル)の中の `{{名前}}` に差し込みます(下の「指示書に差し込む値」)。
- **トークンの伏せ字:** ワーカーは自分のトークンを出力に書けます。事務局はトークンの値を持たないので、ログと要約を残す前に、書き方(`sk-ant-` で始まる文字列)で見つけて伏せます。
- **使わないもの:** `--bare` は使いません。サブスクリプションのトークンを読まなくなり、`CLAUDE.md` の読み込みも止まるからです。
- **版の固定:** Claude Codeの版は、ワーカーのイメージで固定します。フラグの挙動が版で変わっても、気づかないうちに動きが変わらないようにします。

### 指示書に差し込む値

指示書には、値を差し込む場所を `{{名前}}` と書きます。呼び出す側は、名前と値の組を渡します。

| 指示書 | 差し込む値 |
| --- | --- |
| `plan` | `issue`(タイトル、本文、コメント)、`factory_yml` |
| `implement` | `issue`、`factory_yml`、`plan`(計画の本文)、`feedback`(差し戻しの指摘。初回は空) |
| `review` | `issue`、`factory_yml`、`diff`(既定のブランチからの差分)、`test_result`(テストとlintの結果) |

- **欠けている値:** 指示書にある名前の値が渡されていなければ、起動係を呼ぶ前に失敗します。指示書にない名前の値が渡された場合も、同じく失敗します(名前の打ち間違いに気づくためです)。空文字は、渡したものとして扱います。
- **置き換えは1回だけ:** 値はイシューの本文など外から来た文章なので、値の中に `{{名前}}` があっても展開しません。
- **置き場所:** 差し込む場所は、指示書の末尾の「入力」の節にまとめ、値ごとにタグで囲みます。指示書には、そこから後ろがデータであり、指示ではないことを書きます。
- **状態の絞り込み:** `--json-schema` に渡す状態の一覧は、指示書ごとに、返せるものだけにします。指示書に書いた状態の一覧と、呼び出し側が受け付ける状態が一致していることは、テストで確かめます。
- **確認:** `scripts/check-prompts.sh` で、仮の小さな製品と小さなイシューを使い、3つの指示書を実際に1回ずつ呼び出して確かめます。`implement` と `review` が `done` を返したときは、要約が指示書で決めた見出しをその順で持つことも、ここで確かめます(事務局は、要約の中身を検査しません)。指示書を変えたときは、これで確かめ直します。

司令塔(段階2)の呼び出し方は、ここでは決めません。

## ダッシュボード

最初は読み取り専用で作り、操作(停止、再開、手動の再試行)は後の段階で足します。

| 画面 | 見えるもの |
| --- | --- |
| 概況 | 状態ごとのイシュー数、進行中の実行、人間の対応待ち一覧、当日の費用 |
| イシュー | 一覧と、1件ごとの履歴(遷移、判断、実行) |
| 実行 | ステップの進み具合、ログ、費用、PRへのリンク |
| 判断ログ | 司令塔の指示と理由、却下された指示 |
| 定期タスク | 一覧、次回の実行時刻、有効・無効 |

外部には公開せず、最初はSSHのポート転送で開きます。実行中のエージェントをその場で眺めたいときは、herdrを併用します。

## 段階的な進め方

6段階に分け、段階2までは実験用リポジトリで進めてから実プロジェクトに向けます。

| 段階 | 範囲 | 確認方法 |
| --- | --- | --- |
| 0. 骨組み | DB、マイグレーション、GitHubのポーリング、遷移表、テスト | イシューを作るとDBに入る。遷移表の単体テストが通る |
| 1. ワーカー | 手動で `ready` にしたイシュー1件をPRにする | 小さなイシューでPRができる。途中で落として再起動しても続きから進む |
| 2. 司令塔 | 分類と着手指示の自動化 | 新規イシューが自動で分類され、不明点には質問コメントが付く |
| 3. ダッシュボード | 読み取り専用の画面 | 状態と判断ログを画面で追える |
| 4. 定期タスクと報告 | スケジュール、日次報告 | 定時にイシューが起票され、朝に報告が出る |
| 5. 対話エージェント | 対話での起票、質問への回答の取り次ぎ | 対話で起票でき、回答すると作業が再開する |

段階1を最初の山に置くのは、ヘッドレス実行の癖(権限、上限、静かな失敗)が早く分かるからです。段階5までは、このチャットや手動の起票で代用できます。

## 段階1の決定

段階1(ワーカー)の実装を左右する未決事項を、次のように決めました。理由と詳細は、右の列の節にあります。

| 項目 | 決定 | 書いてある節 |
| --- | --- | --- |
| Claudeの呼び出し方 | `claude -p` をサブプロセスで呼ぶ | 技術構成 > Claudeの呼び出し方 |
| ワーカーの認証 | サブスクリプションの長期トークンを、Claudeを呼ぶコンテナにだけ渡す | ワーカーの封じ込め > Claudeの認証と利用量の上限 |
| 1日の予算上限 | 金額ではなく、1日に着手する実行の数で守る(既定20) | 同上 |
| ワーカーの隔離 | ステップごとに使い捨てのコンテナ | ワーカーの封じ込め > 隔離と起動 |
| 事務局からの起動 | Dockerソケットを持つ起動係に依頼する。事務局はコンテナのまま | 同上 |
| 外向き通信の制限 | 内部ネットワークとプロキシ。段階1では内部宛てだけを拒否する | ワーカーの封じ込め > 外向き通信 |
| cloneと作業場所 | 事務局専用のミラーと、イシューごとの独立したclone。所有者は事務局の実行ユーザー | ワーカーの封じ込め > 作業場所 |
| 試行上限と待機時間 | `limits.max_attempts`(既定3)、5分・30分・2時間 | ワーカーの実行手順 |
| 段階1での着手 | 優先度の高い順、同じならイシュー番号の若い順 | イシューの状態と遷移 > 段階1での着手 |
| 同時実行数の上限 | `limits.max_parallel`(既定1)のまま、1件から始める | 製品側の契約 |

### 設計の原則との照合

| 原則 | 決定との関係 |
| --- | --- |
| 事務局は判断しない。司令塔は実行しない | 着手の順、1日の上限、待機時間は、どれも固定の規則と数値で、事務局は当てはめるだけ |
| GitHubが正 | 変更なし。優先度も `priority:` ラベルから読む |
| GitHubへの書き込みは事務局だけ | 変更なし。起動係とワーカーは、GitHubのトークンを持たない |
| ワーカーにGitHubとDBの資格情報を渡さない | GitHubのトークンとDBは見えない。Claudeのトークンだけは渡す(下の「原則の文言の変更」) |
| 遷移表にない遷移は実行しない | 段階1の着手は、表にある `ready` から `in-progress` への遷移で、実行者も事務局のまま。条件のうち司令塔の指示を、固定の規則で代える |
| mainへのマージは人間だけ | 変更なし |

### 原則の文言の変更

`CLAUDE.md` の「ワーカーに資格情報を渡さない」は、見出しだけを読むと、Claudeのトークンも渡さないように読めました。本文は「GitHubのトークンもDBも見えない環境で動く」なので食い違いではありませんでしたが、リポジトリの持ち主の承認を得て、次のように明確にしました。

- **変更後:** 「ワーカーにGitHubとDBの資格情報を渡さない。ワーカーはGitHubのトークンもDBも見えない環境で動く。ワーカーが持つのは、Claudeを呼ぶためのトークンだけとする。」
- **理由:** ワーカーはClaudeを呼ぶので、そのトークンだけは環境に置かざるをえません。例外を原則に書いておくと、ほかの資格情報を足す変更を、原則に反するものとして見分けられます。
